# Submission assembly

Outcome: a formatted Word file built from the manuscript with the selected output profile, with its full content preserved without unauthorized changes, checked against each adopted rule both mechanically and by inspecting the rendered pages. Report what passed and what needs attention. On request, a frozen release in `outputs/releases/`. A file that opens is not a compliant file.

## Step 1: Identify the current content and format source

1. First read `manuscript/manifest.yaml` and its selected content and metadata. If it lists no section, report that no maintained Word manuscript can yet be assembled and ask for adoption or content; stop before reading export internals or installing tools. For an explicit request only to copy an existing file, keep that separate from assembly. Identify the requested format file in `inbox/` or its import record before selecting a profile. A supplied manuscript can be a style example even without a separate template; use a source-specific profile when it is named. Otherwise use the selected venue profile, or a neutral profile when neither is specified. A style example does not select a submission venue.
   The assembled content comes from the current manifest and metadata. The archived original supplies format evidence, not replacement content. Read [export reliability](../../../docs/export-reliability.md) when using an imported draft or example Word file, when tables contain HTML or merged cells, or when conversion or rendering fails. It defines the sample check, recovery, and delivery boundaries.
2. Run `python scripts/export.py tools`. If Pandoc, pandoc-crossref, or mermaid-cli (for diagrams) is missing, explain what each is for and its size, and install only with consent: `python scripts/export.py install --component pandoc --component crossref [--component mermaid]`. Use `environment-management` when Node.js or a browser is missing. Writing never depends on these tools.
3. Create a missing profile: `python scripts/export.py profile-init --id <venue-id> --name "<venue name>"`. It creates the profile's `templates/` folder, `profile.yaml`, and Pandoc's default Word styles. Write an English `README.md` in the profile folder describing its role and linking to `templates/`, `requirements.md`, `profile.yaml`, and the reference document. When `originals/` is created, add a README that says supplied files remain unchanged; add a README to `templates/` that describes its actual contents.

## Step 2: Gather and keep the sources

4. Copy each supplied guideline, Word or LaTeX template, and example article into the profile's `originals/` unchanged. Read the current official guidelines named in the venue note in `research/venues/` as well, and note the version or date of each source.
5. A PDF example shows a layout; it is not an executable template and not automatically the current specification. A Word example also contains direct formatting, merged cells, section breaks, and object placement that Pandoc's reference document does not reproduce automatically. Inspect its actual page and paragraph properties as well as styles; do not promise matching pagination from `reference_doc` alone. Text extracted from a document helps reading, but the original stays the source.

## Step 3: Adopt the rules

6. Extract the explicit rules that the output must meet: page and margins, fonts by language and text role, sizes, emphasis, spacing, headings and their numbering, title page and author information or anonymization, abstract and keywords, section order and required sections, citation and reference style, figure and table placement, captions and numbering, table appearance, equation numbering, line numbers, length limits, and file requirements. When restoring a supplied format, font and table-style fidelity are required alongside content and structure. Follow the [font and table restoration procedure](../../../docs/export-reliability.md#restore-fonts-and-table-appearance); record the observed settings by text role and table rather than imposing one global font or one default table style.
7. Write them in the profile's `requirements.md`, in English, one section per rule with the layout in `requirements/profiles/README.md`: the rule, its source and location, the implementation, the check, the latest result, and how it was confirmed. Adopting a supplied template or guideline authorizes its explicit rules. A request to use an example's format authorizes reproducing its observable layout for this output; record those observations as example-derived, not venue rules. Ask one question only when conflicting sources or an unclear interpretation materially changes the requested result. Do not ask again whether to use the file the researcher already named.
8. Content that a rule requires but the manuscript lacks (a structured abstract, a data availability statement) is reported as missing. Never invent it, and never delete material to fit a limit; those are the researcher's decisions.

## Step 4: Implement the rules

9. Put Word styles and page setup in the reference document: `python scripts/export.py reference-doc --profile <id> [--page A4] [--margins-cm 2.5] [--font "..."] [--east-asian-font "..."] [--size-pt 12] [--line-spacing double] [--space-after-pt 0] [--table-line-spacing single] [--heading-font "..."] [--heading-color black] [--line-numbers yes]`. The settings are kept in `profile.yaml`, so the document can be rebuilt. When the venue supplies its own Word template, try it as `reference_doc` in `profile.yaml` and compare the result; record what it does and does not control.
10. Put the other settings in `profile.yaml`: section numbering, cross-reference words in the manuscript language (`figure_prefix`, `figure_prefix_plural`, `table_prefix`, `equation_prefix`, `section_prefix`, `figure_title`, `table_title`), `table_equations`, `anonymize`, and a CSL style in `templates/` when the venue sets one (`csl:`; obtain an official style only with the researcher's consent for the download). Add the checkable expectations: `expect_page`, `expect_margins_cm`, `expect_font`, `expect_size_pt`, `expect_line_spacing`, `expect_line_numbers`, `expect_max_words`, `expect_anonymized`.
    Those settings do not cover every font run or table property. Preserve effective source fonts and table appearance through derived reference styles and, where necessary, a tested export transform. Keep it reproducible and run it before final verification and output hashing. Do not overwrite tuned source-derived styles with a new default reference document. If the current pipeline cannot express a required property, implement and check the missing transform or mark the requirement unmet; do not claim that the profile already handles it.

## Step 5: Build, inspect, and repair

11. Run `python scripts/manuscript.py check`, then check the conversion risks before a full build. For imported HTML tables, merged headers, complex equations, or heavily formatted examples, test the affected construct in an ignored, isolated sample with the installed converter and filters. Inspect the parsed structure and rendered sample; correct labels in the source do not prove that the converter recognizes a table. Follow the reliability guide before changing a filter.
    For every export, preserve and fingerprint the current selected content before conversion. Follow [content preservation](../../../docs/export-reliability.md#preserve-complete-content-without-rewriting) to reconcile that baseline with the final DOCX and its rendered output. Check all content, not only a sample or object counts. Formatting authorization does not authorize rewriting, correcting values, translating, deleting material, or adding example text.
    Build: `python scripts/export.py build --profile <id> --render [--renderer word|libreoffice]`. The build blocks on manuscript integrity or output-loss issues, including unconverted raw content for another format. It also reports layout expectations, length, and open `[TODO: ...]` markers; these findings do not by themselves block a preview. `build.json` distinguishes blocking checks from notes. A passed build is a mechanical check, not visual approval. A manuscript without metadata builds with no title block; report missing required front matter without inventing it. Zero citation keys means no keyed citations were checked; preserved author-year text is not evidence of resolved or verified references.
12. Inspect the rendered PDF page by page against every rule in `requirements.md`: layout, fonts for each language and text role, spacing, headings, title block, abstract, captions and numbering, equations, citations and references, figures at printed size, tables, line numbers, and page breaks. Reconcile tables cell by cell, including merged headers, values, signs, notes, row/column counts, and widths. Compare table borders, shading, cell margins, row heights, text alignment, typography, and page-spanning behavior with the format source. Inspect all pages a table spans. Verify effective fonts and actual font use in the rendered output; a matching default font or table style name alone does not pass restoration. Compare publication components with the confirmed paper language; report mismatches without translating them during formatting.
    Select and name the renderer. If Word fails, check its diagnostic and any visible dialog; do not repeat an unchanged command. An installed LibreOffice can provide a local review preview using `render --docx ... --renderer libreoffice`; state that its layout can differ. If the request requires Word verification, keep that requirement unmet until Word is checked. The `.render.json` receipt links the PDF to the DOCX and renderer; it does not record visual approval. Keep useful failed-build records and inspection evidence.
13. Repair the profile, templates, or filters, never the scientific content, and rebuild after each tested correction. When the same failure remains, diagnose a minimal sample rather than repeat the full pipeline. Keep a specific unsupported construct visible if repair cannot be verified. Record each rule separately as passed, failed, or not checked, with the file and renderer actually assessed; do not combine all formatting into one blanket pass. If a maintained manuscript needs a syntax repair, preserve its prior version, compare meaning and identities, and synchronize its argument map and reasoning register under the logic map guide.

## Step 6: Deliver

14. Report in the interaction language: whether the file is a rebuild of the current manuscript or an original-file copy, the profile, checks and inspection scope, unresolved issues with their effect, and file locations. Verify that the delivered rebuild matches the current inputs with `verify --profile <id>`. A preview is not a submission. Do not replace a failed rebuild with an archived original and call the export complete. If the researcher requested a copy, label it as a copy; otherwise report the rebuild incomplete and ask about a copy only if useful. Matching two original-file hashes proves copy identity, not agreement with the current manuscript. Do not delete a failed `build.json` to present another file as passed.
    Record the content comparison against the exact delivered file, its input baseline, documented representation changes, differences and their dispositions, and any unchecked scope. Any unexplained addition, omission, changed value or wording, duplication, or order change blocks an unchanged-content claim and final-package completion. An incomplete check stays incomplete even if `build` or `release` accepts the file; those commands currently do not provide full content reconciliation. Recheck after every repair or post-processing change.
15. When the researcher asks for the final package, first confirm that publication components use the target paper language or report the specific unresolved mismatch for a research decision. Write a concise English release description at `outputs/preview/<profile>/release-README.md` from the actual build record, stating the manuscript file, profile, build date, and any nonblocking layout or length notes and open items allowed by the researcher. Then freeze it: `python scripts/export.py release --profile <id> --id <release-id> --readme outputs/preview/<profile>/release-README.md`. It accepts only a current build whose blocking checks passed, copies that README into the package, refuses open `[TODO: ...]` markers unless the researcher confirms a release with open items, and never overwrites a release. A release is not a submission; submitting is the researcher's separate action.

## Completion check

- Every adopted rule has a source, an implementation, a check, and a recorded result; inferred or conflicting rules were confirmed first.
- The build passed its checks, and the rendered pages were inspected against each rule; the application that rendered them is named.
- For a supplied format, fonts and table appearance were restored and compared with that source. Missing fonts, substitutions, and unmatched properties remain explicit failed or unchecked requirements, not a blanket pass.
- The delivered file contains the current selected content. A source copy is explicitly identified and never treated as a passed rebuild.
- All selected text and objects were reconciled with the final DOCX and rendered pages, source files remain unchanged, and every representation difference is explained. Content completeness and unchanged-content status are recorded separately from formatting. Unexplained differences or unchecked content block completion.
- No scientific content was rewritten or removed for layout, and missing content is reported, not invented.
- A release, if made, is a current passing build, frozen and never overwritten.
